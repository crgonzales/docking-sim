# Visual Pass Implementation Plan

> **Superseded (visual scope):** the sky/atmosphere/cloud/relief scope of this plan was re-planned and delivered by `F_0.8.0_sky-overhaul.plan.md` (Codex-approved 2026-08-16). The glTF model + livery gate carried over unchanged.


## Overview

v0.8.0 rebuilds the planet's visual fidelity to a Scatterer + EVE standard: real
atmospheric scattering replacing the current flat fresnel halo, two independently
drifting cloud layers with the main deck casting shadows onto the surface, 4k Earth textures with
anisotropic filtering, the normalized glTF craft models that have been a
documented follow-up since v0.2.0, and LUCKY MARLIN hull livery on the chaser. Physics, flight software, and scenario logic
are untouched — this release is entirely `apps/web` rendering plus assets.

## Problem Statement

The scene reads as low-fidelity for three independently diagnosable reasons:

1. **Textures are 2048×1024** (`ASSETS.md`) on a globe that fills half the frame,
   and no `anisotropy` is set — so the limb, which is most of a sphere's visible
   area, smears at grazing angles. Resolution and filtering are both limiting.
2. **The atmosphere is one fresnel term.** `Earth.tsx` renders a `BackSide` shell
   at 1.03× with `rim = pow(1.0 - abs(dot(n, viewDir)), 3.0)` and a single
   `rimColor`. That produces a uniform blue halo of constant hue — no wavelength
   dependence, no optical-depth variation, and no warm forward-scatter at the
   terminator, which is exactly what makes real limb views read as air.
3. **There are no clouds at all** — never implemented, not a regression.

Separately, the craft are still code-drawn primitives: `USE_GLTF_MODELS` in
`Spacecraft.tsx` has been `false` since v0.2.0 with the Suspense and
error-boundary path already written and unused.

## Solution Architecture

**Scattering, analytic not raymarched.** ARCHI.md commits to 60 fps on integrated
GPUs and that constraint is being held, so the atmosphere uses a closed-form
approximation rather than per-pixel optical-depth integration: analytic chord
length through the shell for view-angle-dependent thickness, wavelength-dependent
Rayleigh coefficients (β ∝ 1/λ⁴, so blue scatters ~5.5× red), a Rayleigh phase
term, and a Mie-style forward-scatter lobe that supplies the warm terminator glow.
This is the single most important quality decision in the plan: it buys most of
Scatterer's look at a fixed, budgetable fragment cost.

**Clouds as two spheres, shadows as a texture fetch.** A main deck and a thinner
high cirrus layer at different radii rotate at different rates, giving parallax as
the camera orbits. Shadows are approximated by sampling the cloud alpha inside the
*surface* shader at a UV offset derived from the sun direction — one extra texture
fetch, no shadow map, no second pass. Shadows are what make clouds read as
floating rather than painted on.

**Craft models: normalize at load, not in the asset pipeline.** Rather than
requiring perfectly pre-normalized `.glb` files, the loader applies the
`ASSETS.md` contract (meter scale, COM pivot, target port −ŷ, chaser axis +ŷ) at
runtime from declared per-model transforms. That keeps arbitrary NASA 3D Resources
drops usable and keeps the existing primitive fallback meaningful.

**No sim-core or scenario changes whatsoever.** Nothing here touches dynamics,
FSW, telemetry, or the scenario package. The package boundary makes that
structural rather than a promise.

## Implementation Details

### 1. Texture upgrade and filtering

**File**: `apps/web/public/assets/textures/` (new files), `apps/web/src/scene/Earth.tsx`

**Current state**: three 2048×1024 maps loaded via `useLoader(TextureLoader, …)`;
`colorSpace` set on day and night maps; **no anisotropy set on any texture**.

**Modifications**:

- Replace the **day and night** maps with 4096×2048 equivalents sourced from NASA
  Visible Earth (Blue Marble Next Generation and Earth at Night), which are public
  domain — matching the licensing posture of the existing NASA-derived maps and
  deliberately avoiding new attribution obligations. **The spec/water mask stays at
  2048×1024 and single-channel**: it is a low-frequency binary-ish mask feeding one
  glint term, so 4k RGBA would cost ~45 MB resident for no visible gain.
- Set `texture.anisotropy` from `renderer.capabilities.getMaxAnisotropy()` on every
  Earth-surface and cloud texture. Access the renderer via `useThree()`; do not
  hardcode a value, since the cap is device-dependent.
- Keep `SRGBColorSpace` on colour maps; the spec/water mask is **data, not colour**
  and must stay linear — setting sRGB on it would silently distort the glint term.
- Mip chains matter as much as anisotropy for the grazing-angle smear, but **three.js
  will not generate them for KTX2**: compressed textures cannot be mipped at runtime,
  so the chain must be authored offline (see the KTX2 notes under Performance). Only
  uncompressed fallback textures get three.js's automatic power-of-two generation.

### 2. Cloud layers

**File**: `apps/web/src/scene/Clouds.tsx` (new), `apps/web/src/scene/Earth.tsx` (mount)

**Modifications**:

- Two `sphereGeometry` shells inside the existing Earth `group` so they inherit its
  position: a main deck at ~1.004× radius and a thin cirrus layer at ~1.008×.
  Segment count may be lower than the surface's 96×96 — cloud silhouette detail
  comes from the alpha map, not geometry.
- A shared `ShaderMaterial` (two instances with differing uniforms) sampling a
  cloud alpha map, lit by the same `sunDir` the surface uses so the terminator
  stays consistent. Clouds must go dark on the night side but retain a faint rim
  where they catch grazing sunlight — a hard cutoff looks wrong.
- **Compositing must be stated explicitly.** `ShaderMaterial` defaults to
  `transparent: false` with `depthWrite: true`, which would make an alpha-sampling
  cloud shell an opaque sphere that hides the Earth and the other layer. Both
  shells therefore need `transparent: true`, `depthWrite: false`, and an explicit
  `renderOrder` giving back-to-front draw: **surface → main deck → cirrus →
  atmosphere**. Clouds use normal alpha blending, not the additive blending the
  atmosphere and plumes use — additive clouds would glow rather than occlude.
  `depthTest` stays on so the planet still occludes clouds on the far limb.
- Independent rotation per layer, advanced in `useFrame`. **Rotation is a
  render-side visual effect only** — it must not read sim time, feed back into any
  store, or imply the Earth is rotating in the physics model.
- Cloud alpha map from the NASA Blue Marble cloud layer (public domain).

### 3. Cloud shadows on the surface

**File**: `apps/web/src/scene/Earth.tsx` (surface fragment shader)

**Modifications**:

- Pass the cloud map and the main deck's current rotation offset into the surface
  shader as uniforms.
- Sample cloud alpha at a UV offset along the sun direction projected into surface
  UV space. The offset magnitude corresponds to the deck's altitude above the
  surface and the sun's incidence angle — it should lengthen toward the terminator,
  which is both physically right and visually where shadows are most legible.
- **Introduce a separate `sunVisibility` factor; do NOT attenuate `dayness`.** The
  existing shader computes `dayness = smoothstep(-0.12, 0.18, ndotl)` and then uses
  it for *both* daylight and, inverted, for city lights:
  `night = texture2D(nightMap, vUv).rgb * nightGain * (1.0 - dayness)`. Scaling
  `dayness` down for shadow would therefore make city lights **brighter** under
  clouds — precisely backwards. Instead apply `sunVisibility` only to the direct
  solar terms (`day * dayness` and `glint`), leaving the `night` term driven by the
  unmodified `dayness`.
- Shadows must not darken the night side — there is no sunlight there to block.
- **Shadows come from the main deck only.** The cirrus layer is thin and high; a
  second independently-rotated fetch would double the per-fragment texture cost for
  a barely visible contribution, against a 60 fps budget that is already the
  binding constraint. Cirrus contributes parallax, not shadow.

### 4. Atmospheric scattering rewrite

**File**: `apps/web/src/scene/Earth.tsx` (atmosphere shader)

**Current state**: `BackSide` sphere at 1.03×, additive, `depthWrite: false`,
fragment is a single `pow(1 - |dot(n, v)|, 3.0)` rim times a night fade, with one
uniform `rimColor` (`#4d7dff`).

**Modifications**:

- Replace the single rim term with an analytic scattering model:
  - **Optical depth**: analytic chord length of the view ray through the
    atmosphere shell, so thickness grows toward the limb instead of being a fixed
    fresnel curve.
  - **Rayleigh coefficients**: per-channel β ∝ 1/λ⁴, giving deep blue overhead and
    the characteristic desaturation into white/orange as path length grows.
  - **Rayleigh phase**: `(1 + cos²θ)` in sun-view angle.
  - **Mie forward-scatter lobe**: a Henyey-Greenstein-style term with strong
    forward bias, producing the warm glow concentrated near the terminator. This
    term is what visually separates "Scatterer" from "blue halo".
  - **Angle convention must be stated in the shader.** The existing code computes
    `ndotl = dot(n, sunDir)` and treats positive as lit, so **`sunDir` points from
    the surface toward the sun** — it is not the light-travel direction. Forward
    scattering is defined on the direction light actually travels, so the phase
    angle must use `-sunDir` against the view vector. Getting this backwards puts
    the warm glow on the wrong limb, and it will look plausible enough at a glance
    to survive an inattentive review — assert the sign with a deliberate check
    against a known sun position.
- Keep the shell additive with `depthWrite: false`, and **respect the established
  HDR/bloom contract** — the scene runs half-res bloom where only deliberate
  highlights exceed luminance 1.0. The terminator glow may exceed it; the broad
  limb must not, or bloom will wash the frame.
- The shell may need to grow beyond 1.03× for a believable limb; if so, verify it
  does not clip the near plane or intersect the chaser at close range.

### 5. glTF craft models

**File**: `apps/web/src/scene/Spacecraft.tsx`, `apps/web/public/assets/models/`

**Current state**: `USE_GLTF_MODELS = false` at line 20, `TARGET_MODEL_URL` /
`CHASER_MODEL_URL` declared, a `<primitive object={scene} />` path and an explicit
error boundary already written (Suspense covers loading, never errors), and
`useGLTF.preload` already flag-guarded.

**Modifications**:

- Apply the `ASSETS.md` normalization contract at load time from a declared
  per-model transform (scale, rotation, pivot offset) rather than assuming the
  `.glb` arrives pre-normalized: meter scale, pivot at vehicle COM, target docking
  port facing −ŷ, chaser docking axis +ŷ.
- **Register against the sim's fixed contact anchors — this is the constraint that
  makes or breaks the models.** `sim.ts` hardcodes `STATION_PORT_HILL = [0, -8.7, 0]`
  and `CHASER_PORT_BODY = [0, 1.7, 0]`, and docks the chaser COM at y = −10.4 with
  identity `q_BH`. Normalization is therefore **not** free: after transform, the
  chaser model's docking port must sit at exactly `+1.7 m` along body ŷ from its
  pivot, and the station model's port must sit at `−8.7 m` in Hill ŷ. Any mismatch
  shows as a visible gap or interpenetration at the moment of capture — the single
  most scrutinised frame in the whole sim.
- **Also register the hull against jet positions.** Plumes emit from
  `DRACO_THRUSTER_GEOMETRY` at body `x = ±1.2`, `y = ±0.8`, `z = ±0.45`. The
  requirement is that each jet origin sits **on or just outside the hull surface,
  with clear space along its outward exhaust direction** — not that the hull
  encloses the jets, which would bury every plume inside the mesh. If the hull
  extends past a jet origin, that plume renders inside geometry and disappears; if
  the hull is far inside, plumes float detached. The model's scale must be chosen so
  the hull surface sits near those jet locations, or the jet positions themselves
  must be revisited — and changing them is a **sim-core change outside this
  release's scope**, so the model must adapt, not the physics.
- Verification is geometric and checkable: assert post-transform port offsets equal
  the sim constants within a small tolerance, rather than eyeballing the dock.
- Flip `USE_GLTF_MODELS` **only once models are present and verified**; the
  primitive fallback stays as the error path, not dead code.
- Record each model's source, licence, and applied normalization transform in
  `ASSETS.md`, per that file's own stated convention.
- **Dependency (not automatable):** the `.glb` files must be obtained and placed
  by the repo owner. NASA 3D Resources models require download and typically a
  Blender pass. This is a human checkbox — the *code* path is implementable now
  and can be verified against any placeholder `.glb`.

### 6. Craft livery — LUCKY MARLIN logo

**File**: `apps/web/src/scene/Spacecraft.tsx`, `apps/web/public/assets/textures/lucky_marlin_logo.png`

**Current state**: the chaser is an untextured primitive — a cylinder body with
`meshStandardMaterial color="#b8bcc4"`. No decals or markings anywhere.

**Modifications**:

- Apply the supplied `LUCKY MARLIN` mark as hull livery on the chaser. The asset is
  already prepared: cropped to content, white keyed to alpha with antialiased edges
  preserved, and fitted to a 1024×512 power-of-two canvas.
- **Pick the target mesh deliberately — the two hull sections differ.** The main
  capsule is `cylinderGeometry(1.1, 1.9, 3.4, 20)`, a **tapered frustum**, so a
  constant-radius cylindrical patch will not conform to it. The service module at
  `y = -2.4` is `cylinderGeometry(1.9, 1.9, 1.4, 20)` — genuinely constant radius.
  Therefore: either **(a)** a cylindrical patch constrained to the *service module*,
  or **(b)** `DecalGeometry` (or a matching conical patch) if the logo goes on the
  *tapered capsule*. A flat quad is acceptable on neither.
- Orient it on the hull **side**, clear of the ±ŷ docking axis, which must stay
  visually clean and is occluded at capture anyway.
- **Verify from a three-quarter view, not the default chase.** `viewStore.ts` sets
  `CHASE: { azimuth_rad: 0, elevation_rad: 0.25 }`, which looks essentially down the
  ŷ axis — a side decal is edge-on and unreadable from it. Use the `CINEMATIC`
  default (`azimuth_rad: 0.52, elevation_rad: 0.42`) as the acceptance view, or
  orbit the chase camera off-axis. If the livery should read from the default chase
  view specifically, the initial chase azimuth must be changed — call that out as a
  deliberate decision rather than discovering it looks wrong later.
- Alpha-blended, `depthWrite: false` if offset above the hull, with a small
  polygon-offset or radial epsilon to avoid z-fighting against the body.
- The livery is **colour data**: set `SRGBColorSpace` on it, matching the day/night
  maps. Omitting it renders the navy noticeably washed out.
- **The glTF flag flip is GATED on the livery being reattached — not merely
  reviewed.** A real model carries its own UVs and geometry, so decal placement does
  not transfer; without a gate, enabling `USE_GLTF_MODELS` silently ships an unmarked
  chaser and the omission is easy to miss because nothing errors. Therefore
  `USE_GLTF_MODELS` may only be set `true` once the livery has been **implemented and
  visually confirmed on the normalized glTF chaser**, not once it has been noted as
  outstanding. Keep the livery a separate, repositionable element rather than baking
  it into the primitive geometry, so reprojection is a placement change rather than a
  rewrite.
- Provenance: user-supplied original artwork for a fictional contractor; no
  third-party licence obligation, unlike the ESO asset below. Record it as such in
  `ASSETS.md`.

## Technical Considerations

- **Pattern Usage**: shaders follow the existing `Earth.tsx` structure — module-level
  GLSL constants, `ShaderMaterial` built in `useMemo`, uniforms mutated rather than
  materials rebuilt. `ThrusterPlumes.tsx` (v0.7.0) is the reference for an
  allocation-free `useFrame`.
- **Package Boundary**: entirely `apps/web` plus assets. No sim-core or scenario
  imports, changes, or new dependencies on them. Cloud rotation is render-side only
  and must not couple to sim time.
- **Conventions**: Earth sits at `-ORBIT_RADIUS_M / EARTH_VIEW_SCALE` on x̂ per the
  Hill-frame convention; the scaled-group and logarithmic-depth setup is load-bearing
  for precision and must not be disturbed. Sun direction stays sourced from `sun.ts`
  so surface, clouds, and atmosphere agree.
- **Determinism**: unaffected — no sim state is read or written. Cloud drift is
  wall-clock render animation and must stay outside any deterministic path.
- **Verification**: shaders have no analytic oracle in the project's usual sense.
  Testable seams are the *pure helpers*: scattering coefficient derivation, the
  shadow UV-offset function, and the model normalization transform. The visual
  result itself is verified by screenshot and by eye; that limitation is recorded
  rather than papered over.
- **Performance**: target is **30 fps on integrated GPUs** (relaxed from 60 by the
  repo owner during implementation, to fund volumetric clouds). Budget is two extra sphere draws, one
  extra texture fetch in the surface fragment, and a heavier atmosphere fragment.
  4k textures roughly quadruple texture memory versus 2k — a real cost on
  integrated GPUs, and the reason 8k was rejected. Verify with all 16 plumes
  firing, since v0.7.0's own 60 fps check is still outstanding.
- **Edge Cases**: camera inside the atmosphere shell at close range; cloud shadow
  UV wrap at the seam and near the poles where equirectangular UVs converge;
  glTF load failure falling back to primitives; missing model files with the flag
  accidentally on; anisotropy unsupported (cap returns 1); night-side cloud
  lighting; bloom blowout when terminator glow meets plume cores.

## Type Definitions

A `CloudLayerConfig` shape (radius multiplier, rotation rate, opacity, texture)
parameterising the two layers.

`ModelNormalization` per craft model must carry enough to *derive* the transform
rather than have it guessed: `scale`, `rotation`, `pivotOffset`, plus **the port
location in the model's own source space** — either a named glTF node
(`portNodeName`) or an explicit `portLocal: Vec3`. Without that, "put the port at
`[0, 1.7, 0]`" is unactionable, because nothing identifies which part of an
arbitrary mesh *is* the port. Include the acceptance tolerance explicitly: post-
transform port position must match the sim anchor within **≤0.01 m**, tight enough
that no gap is visible at docking-camera range.

No shared or exported types leave `apps/web`.

## Performance & Cost Impact

Two additional sphere draws, one extra texture fetch per surface fragment, and a
materially heavier atmosphere fragment shader.

**Transfer size and GPU memory are different budgets, and the second one is the
dangerous one.** Compressed download grows roughly 4–6 MB against a current 5.4 MB
bundle. Resident GPU cost is the real constraint, and the arithmetic below is for
this plan's actual inventory (4k day, 4k night, **2k** single-channel spec, 4k
cloud) — not a naïve three-4k-map configuration.

| Texture | Naïve RGBA + mips | UASTC + mips |
|---|---|---|
| 4k day | ~44.7 MB | ~11.2 MB |
| 4k night | ~44.7 MB | ~11.2 MB |
| 2k spec (single-channel) | ~2.8 MB | ~2.8 MB |
| 4k cloud | ~44.7 MB | ~11.2 MB |
| 1024×512 livery (RGBA PNG, uncompressed) | ~2.8 MB | ~2.8 MB |
| **New-asset subtotal** | **~140 MB** | **~39 MB** |
| Existing 4k starmap (plain JPEG → RGBA) | ~44.7 MB | ~44.7 MB |
| **Total against the ≲96 MB gate** | **~185 MB ✗** | **~84 MB ✓** |

Uncompressed is decisively over budget; UASTC lands under it with roughly **12 MB
of headroom** — which is the entire allowance for the glTF models' own textures.

**Concrete trigger for the optional starmap conversion:** convert it to KTX2 when
either the measured total exceeds ~88 MB or the craft models' textures exceed
~12 MB. At ~45 MB the starmap is the largest single consumer — bigger than
everything this release adds combined — so it is the first place to look if the
gate is missed, before degrading the Earth maps this release exists to improve.

Required mitigations, to be verified rather than assumed:

- **Compress on the GPU, not just on the wire.** Ship the 4k maps as KTX2 /
  Basis Universal (three.js `KTX2Loader`) so they stay compressed *in VRAM*,
  typically a 4–6× reduction. Plain JPEG/PNG decompress to full RGBA on upload and
  buy nothing here. **`KTX2Loader` has non-obvious setup requirements that must be
  planned, not discovered:**
  - It throws unless `detectSupport(renderer)` is called before the first load, so
    it needs the renderer — obtain it via `useThree()` and initialise before any
    texture request.
  - It requires the Basis transcoder assets (`basis_transcoder.js` and
    `basis_transcoder.wasm`, from `three/examples/jsm/libs/basis/`) to be copied
    into `apps/web/public/` and pointed at with `setTranscoderPath()`. These are
    runtime-fetched, not bundled — forgetting them fails only in the browser.
  - Use a **single page-lifetime loader instance**, not one per component —
    multiple instances each spin up their own transcoder worker. **Do not dispose
    it on Canvas unmount.** `App.tsx` swaps the entire scene out for
    `MonteCarloScreen` when entering ANALYSIS, so the Canvas unmounts and remounts
    routinely; disposing a module singleton there revokes its worker source and
    any later uncached load fails on return to SANDBOX. Either keep it a
    page-lifetime singleton disposed only at application shutdown (simplest, and
    the recommendation), or make it provider-owned and genuinely recreated on each
    Canvas mount — but not a module singleton with mount-scoped disposal, which is
    the combination that breaks.
  - **Mip chains must be generated offline** when authoring the `.ktx2` files
    (e.g. `toktx --genmipmap`). Compressed textures cannot have mips generated at
    runtime, so a KTX2 authored without them silently loses the anisotropy benefit
    this phase exists to deliver.
- **Right-size per map.** The spec/water mask is a low-frequency single-channel
  mask — keep it at 2k and single-channel rather than 4k RGBA. Night lights
  tolerate less resolution than the day map.
- **Downgrade selection is decided once, before loading — not swapped at runtime.**
  Author two complete asset sets (`4k/` and `2k/`). **Exact predicate — select the
  4k tier only when all hold**, otherwise fall back to 2k:
  1. `renderer.capabilities.isWebGL2` is true;
  2. `renderer.capabilities.maxTextureSize >= 8192` (a 4096-max device cannot hold
     the mip-0 comfortably alongside everything else);
  3. The renderer exposes at least one block-compressed extension **valid for the
     Basis mode we author**. Query directly via
     `renderer.extensions.has('EXT_texture_compression_bptc')` (BC7),
     `'WEBGL_compressed_texture_s3tc'` (BC1/BC3),
     `'WEBGL_compressed_texture_astc'`, or `'WEBGL_compressed_texture_etc'` (ETC2).
     **Author every tiered map as UASTC, not ETC1S.** three's `FORMAT_OPTIONS`
     table lists ASTC with `basisFormat: [UASTC_4x4]` and `priorityETC1S: Infinity`
     — meaning ASTC is *never* selected for ETC1S data. An ASTC-only device given
     ETC1S maps therefore satisfies the extension check and still degrades to
     RGBA, which is the exact failure the predicate exists to prevent. Mandating
     UASTC makes the predicate mode-safe across all four families and suits
     hero planet textures, at ~1 byte/px transcoded rather than ETC1S's ~0.5.
     **Do not ask `KTX2Loader.detectSupport()` for the chosen target — it does not
     expose one.** It only records capability flags on `workerConfig` and returns
     the loader; the actual `transcoderFormat`/`engineFormat` is selected
     per-texture inside `getTranscoderFormat(basisFormat, width, height, hasAlpha)`
     *after* the file is parsed. Since we author the `.ktx2` files ourselves, the
     Basis mode (UASTC vs ETC1S) and alpha presence are known inputs, so extension
     availability plus those known properties fully determine whether transcoding
     lands on a block-compressed format or degrades to uncompressed RGBA — and an
     RGBA fallback puts each 4k map back at ~45 MB, collapsing the compression
     premise. Optionally confirm in development by loading a small probe `.ktx2`
     and inspecting the resulting `texture.format`.
  Evaluate after `detectSupport(renderer)` and before the first texture request.
  Deciding up front avoids the disposal complexity and visible hitch of a
  mid-session swap. If
  a runtime swap is ever added, every replaced texture must be explicitly
  `dispose()`d or the old set stays resident and the downgrade makes memory *worse*.
  Should a frame-time trigger be used instead, specify it concretely: median frame
  time over a ≥120-frame window sampled after warm-up, never a single frame.
- **Set an explicit ceiling and a downgrade path**: target ≲96 MB resident texture
  memory.
- **Do not use `renderer.info.memory` as the gate — it does not report bytes.**
  three.js exposes only `{ geometries, textures }` *counts*
  (`WebGLInfo.js`), so it can confirm how many textures are resident but says
  nothing about their size. Instead compute an explicit byte estimate from known
  dimensions, mip levels, and the **transcoded** format three.js actually selects
  per device (roughly 1 byte/px for BC7/ASTC, ~0.5 byte/px for BC1/ETC1S — versus
  4 bytes/px uncompressed), and treat sustained frame time as the authoritative
  pass/fail signal. `info.memory.textures` remains useful only as a leak check.

glTF models add further weight depending on what is supplied and must be budgeted
against the same ceiling when they land.

Purely additive and visual. No API, schema, or save-state surface exists to break.

craft remain the default path until then.

## Test Impact

- No existing test covers rendering, so **no existing test should change**. If any
  sim-core or scenario test moves, something has gone wrong — that is itself a
  useful signal during the gate.
- New pure-helper tests: scattering coefficient derivation (Rayleigh β ordering
  blue > green > red, phase function bounds), cloud-shadow UV offset (correct
  direction relative to sun, wrap behaviour at the seam), and the glTF
  normalization transform (a known input pose maps to the documented convention).
- Shader output itself is not unit-testable here; expect a `COVERAGE-DEBT.md`
  entry rather than a contrived mock, per the project's hard-to-cover policy.
- Manual verification is mandatory and cannot be delegated: 60 fps with clouds,
  scattering, and all 16 plumes active on real hardware; visual check of the
  terminator, limb, cloud shadows, and night side. This release also clears
  v0.7.0's outstanding 60 fps checkbox.
