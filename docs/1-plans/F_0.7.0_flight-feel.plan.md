# Flight Feel Implementation Plan

## Overview

v0.7.0 makes hand-flying the chaser feel like flying something, not nudging it.
Three strands: a manual-specific attitude control path with pilot-selectable
authority so MANUAL can use the vehicle's real torque capability; per-jet
thruster plumes driven by truth-side firings; and a procedural KSP-style
soundscape layered over the existing WebAudio panel layer. AUTO guidance keeps
its current proximity-ops conservatism untouched.

## Problem Statement

Manual flight is inert, and measurement shows two independent causes:

1. **Command authority is capped far below capability.** The canted 16-jet set
   delivers 96–157 N·m against a `[600, 400, 600]` kg·m² inertia — roughly
   9–15 deg/s². `MANUAL` shaping caps rate at 1.5 deg/s and PULSE torque at
   8 N·m (~6% of available), so a 90° reorientation takes ~60 s against a
   physical floor of ~5 s.
2. **The attitude loop is slow and underdamped.** `kp = [120, 80, 120]`,
   `kd = [180, 120, 180]` against those inertias give ωₙ ≈ 0.45 rad/s and
   ζ ≈ 0.34. Measured step response to an 8 deg/s command: 2.44 deg/s at 1 s,
   6.82 at 3 s, overshoot to 10.59 at 7 s, still settling at 15 s.

Raising the cap alone therefore makes tracking *worse* — commanded rate is not
achieved, which is the same failure class as the v0.4.2 over-damping bug. The
gains must move with the limits, and `kp`/`kd` are currently shared with AUTO
through `step()`.

There is also no visual or audible feedback that jets are firing at all, which
removes the main cue a pilot uses to close the loop.

## Solution Architecture

**Split the attitude controller's manual path from its AUTO path.**
`createAttitudeController` gains an optional manual gain set used *only* by
`stepRate` (and the PULSE rate-damping call). `stepAuto` continues to use the
existing `kp`/`kd`, so AUTO behavior — and every AUTO-dependent regression test
— is bit-identical.

**Pilot-selectable authority.** A `LOW`/`HIGH` authority state scales the manual
limits and gains together. `LOW` reproduces today's docking-realistic numbers;
`HIGH` opens up to near-time-optimal. Authority is changed through a public
`SimLoop` command (like `setController`), never a UI-local toggle, so runs stay
deterministic and replayable.

**Scenario pins the authority *level*, not the values.** `packages/scenario`
constructs the sim with `initialManualAuthority: 'LOW'` and **no** per-field
overrides — overriding fields would outrank the preset and make the MISSION
authority switch inert. Because neither the perfect-operator bot nor any
acceptance run ever calls `setManualAuthority`, CI stays on `LOW`, so
`FINAL_APPROACH_01`, the bot, and acceptance test §7.3 are unaffected. **No
scenario schema change** — the level is supplied by the runner, not the scenario
JSON, so `schema_version` stays 1.

**Plumes read truth.** `applyThrusterCommand` already computes
`activeOnTime_s: Record<string, number>` — per-jet on-time *after* stuck-open,
failed, and propellant-depletion effects. `RenderState` is extended to carry it,
so a stuck-open jet visibly fires even when FSW believes it commanded nothing.
This matches the existing truth render channel ("visuals = reality, gauges = FSW
belief").

**Audio is procedural.** `panelAudio.ts` is explicitly synthesized with no
assets; the new layer follows that pattern — no files to load, no CSP or
bundle-size concerns.

## Implementation Details

### 1. Manual gain set and authority scaling

**File**: `packages/sim-core/src/control.ts`

**Current state**: `createAttitudeController` closes over one `kp`/`kd` pair used
by `step()`, which serves both `stepAuto` and `stepRate`. Manual shaping limits
(`maxRate_rps`, `maxVelocity_mps`, `pulseForce_N`, `pulseTorque_Nm`) are
hard-coded defaults at ~lines 217–220.

**Modifications**:

- Introduce a `ManualAuthority = 'LOW' | 'HIGH'` type and an exported
  `MANUAL_AUTHORITY_PRESETS` table holding, per level, the four shaping limits,
  the manual gain pair, and `manualForceLimit_N`. `LOW` = today's values exactly.
  `HIGH` = tuned so the rate loop commands most available jet torque.
- **Precedence (must be explicit).** Resolution order for every manual field is
  **config override > active-authority preset**. There is no third tier.
- **`LOW` inherits AUTO gains by reference, not by value.** `LOW`'s manual gain
  entry is defined as *the resolved AUTO gains* (`kp_Nm_per_rad` /
  `kd_Nms_per_rad`, whatever they resolve to), **not** the literal numbers
  `[120, 80, 120]` / `[180, 120, 180]`. This matters: a caller who configures
  custom AUTO gains today gets those gains in MANUAL too, because `step()` is
  shared. Hardcoding the defaults into the `LOW` preset would silently change
  behavior for such a caller. `HIGH` supplies explicit gains of its own.
- Add `initialManualAuthority?: ManualAuthority` (default `'LOW'`) to
  `AttitudeControllerConfig` so scenarios can pin the level declaratively rather
  than issuing a command at init.
- **Single resolution point.** Add
  `getResolvedManualLimits(): ResolvedManualLimits` (limits **and** resolved gains)
  to the `AttitudeController` interface. Precedence is implemented **once**, here.
  Every consumer — including FSW for the force limit — reads resolved values from
  this accessor rather than re-deriving them from the preset table.
- **Do not overload `step()`.** `fsw.ts:303` uses `attitudeController.step()` for
  **ABORT COASTING** rate damping, and `fsw.ts:365` uses it for PULSE damping —
  the same method. Routing manual gains through `step()` would silently change
  the abort safety path and break the promised AUTO bit-identity. Add a distinct
  manual-damping entry point (e.g. `stepManualDamping`) used by `stepRate` and
  the PULSE call only; `step()` and `stepAuto()` keep AUTO gains and remain
  byte-for-byte unchanged in behavior. The abort path must be covered by a test
  asserting its torque is unaffected by authority level.
- Add `setAuthority(level)` / `getAuthority()` to the `AttitudeController`
  interface. Switching authority must reset the integrator and re-capture the
  rate reference, so a mid-flight change cannot inject a step discontinuity.

**Numeric presets.** `LOW` reproduces today's values exactly:
`maxRate 1.5 deg/s`, `maxVelocity 0.5 m/s`, `pulseForce 40 N`,
`pulseTorque 8 N·m`, `manualForceLimit 60 N`, manual gains = AUTO gains
(`kp [120, 80, 120]`, `kd [180, 120, 180]`).

`HIGH` **starting values**, to be validated (not assumed) by the acceptance case
below:

| Field | HIGH | Basis |
|---|---|---|
| `maxRate` | 8 deg/s | reachable against 9.2–15.0 deg/s² authority |
| `maxVelocity` | 1.0 m/s | force-limited; higher just takes longer |
| `pulseForce` | 55 N | stays under the force cap |
| `pulseTorque` | 45 N·m | ~30% of the 96–157 N·m available |
| `manualForceLimit` | 75 N | of ~114 N one-sided; leaves ~39 N torque headroom |
| `manualKp` | ≈ [740, 490, 740] | ζ ≈ 0.9 against the inertia |
| `manualKd` | ≈ [1200, 800, 1200] | τ = I/kd ≈ 0.5 s |

**Acceptance case (reproducible, replaces "bounded time")**: from rest, full-stick
pitch (`rotation [1, 0, 0]`) at `HIGH` must reach **≥90% of commanded rate within
1.5 s**, **peak ≤110% of commanded** (no more than 10% overshoot), and **settle
within ±5% by 3 s and hold through 10 s**. The same case at `LOW` must reproduce
today's behavior exactly (≥80% of 1.5 deg/s by 3 s, never exceeding 1.8 deg/s).
Gains are free to move as long as this case passes; the table is a starting point,
not a contract.

**Tumble regression for `HIGH` `manualForceLimit` (measurable).** The v0.4.1 bug
was that a translation command stole allocator authority from torque, tumbling
the vehicle. Test it as a paired comparison at `HIGH`, RATE sub-mode, from rest:

- **Baseline run**: `rotation [1, 0, 0]`, `translation [0, 0, 0]`. Record the
  commanded-axis body rate at t = 3 s.
- **Combined run**: `rotation [1, 0, 0]`, `translation [0, 1, 0]` (full forward,
  the input that triggered the original bug).
- **Assert (a) torque tracking survives**: commanded-axis rate in the combined
  run is **≥85% of the baseline value** at the same time index.
- **Assert (b) no tumble**: off-commanded-axis body rates stay **below 1 deg/s**
  throughout, and total attitude excursion about those axes stays **under 15°**
  over a 20 s run.

If either assertion fails, lower `HIGH` `manualForceLimit` toward 60 N rather
than relaxing the thresholds.

### 2. Authority command surface

**File**: `packages/sim-core/src/fsw.ts`, `packages/sim-core/src/sim.ts`

**Modifications**:

- `fsw.ts`: add `setManualAuthority(level)` / `getManualAuthority()` delegating
  to the attitude controller; include the active level in `TelemetryFrame` so
  the HUD and any observer can display it.
- `fsw.ts`: `manualForceLimit_N` becomes authority-scaled. **Ownership rule:**
  `control.ts` owns the *value* (it lives in the authority preset table and is
  resolved by `getResolvedManualLimits()`); `fsw.ts` owns the *application* (it
  clamps the manual force demand). FSW must read the resolved value from the
  controller accessor rather than reading the preset table or keeping its own
  copy, so precedence is implemented in exactly one place. **Constructor mapping:**
  `AttitudeControllerConfig` gains an optional `manualForceLimit_N`, and
  `createFsw` forwards `FswConfig.manualForceLimit_N` into it when building the
  attitude controller. That makes the existing FSW-level option the config-tier
  override inside the single resolver, rather than a second, competing source of
  truth. If both are somehow supplied, the controller config value is the one the
  resolver already sees — FSW must not re-clamp with its own copy.
  **Keep the 60 N value for `LOW`.** For `HIGH`, raise cautiously — one-sided jet
  force tops out near 114 N, and the existing headroom is what prevents the
  v0.4.0 translation tumble.
- `sim.ts`: expose `setManualAuthority` on `SimLoop` alongside the other
  operator commands so it is deterministic and scriptable.

**Note**: `ScenarioSimPort` is `Omit<SimLoop, truth/render getters>`, so adding a
command method widens the port. That is correct — it is an operator command, the
same class as `setController`.

### 3. Scenario pins legacy manual limits

**File**: `packages/scenario/src/` (sim construction site), `FINAL_APPROACH_01` runner

**Modifications**:

- Pin **`initialManualAuthority: 'LOW'`** only. Do **not** pass per-field
  `attitudeControllerConfig` overrides — those outrank presets at every level,
  which would make the MISSION authority switch inert (the override would win
  even after switching to `HIGH`).
- Rationale comment: the perfect-operator bot emits *normalized* commands scaled
  by these limits; unpinned, a limits change silently re-scales its canned inputs
  and can break acceptance test §7.3. Pinning the *initial level* is sufficient
  protection because neither the bot nor any acceptance run ever issues
  `setManualAuthority` — so CI runs stay on `LOW` and stay deterministic.
- A **human** player in MISSION may still switch to `HIGH`; that is intended, and
  cannot affect CI, which is headless and scripted.

### 4. Truth-side per-jet firing in RenderState

**File**: `packages/sim-core/src/types.ts`, `packages/sim-core/src/sim.ts`

**Current state**: `RenderState` carries `t_s`, `r_hill_m`, `v_hill_mps`, `q_BH`
only. Critically, `applyThrusterCommand` is called **once per truth tick**
(`window_s: TRUTH_TICK_S`, 10 ms) inside the truth loop, with the FSW pulse
spread across ticks via `remainingOnTimes` — not once per 100 ms FSW window.

**Modifications**:

- Extend `RenderState` with per-jet duty normalized to 0–1.
- **Accumulate, do not sample.** Latching only the most recent truth tick would
  hide or alias normal short pulses (a 30 ms pulse would flicker across three of
  ten ticks, and the ~60 Hz render loop would sample it inconsistently).
  Instead: accumulate `activeOnTime_s` per jet across the truth ticks of the
  current FSW window, and at the FSW boundary latch
  `duty = accumulated / FSW_WINDOW_S` and reset the accumulator. That yields a
  stable 10 Hz duty signal that faithfully represents total on-time.
- `getRenderState()` returns a defensive copy, consistent with the existing
  clone discipline in that function.
- The latched value persists between FSW boundaries so the faster render loop
  reads a steady duty rather than a partially-accumulated one.

### 5. Thruster plume rendering

**File**: `apps/web/src/scene/Spacecraft.tsx` (modify), `apps/web/src/scene/ThrusterPlumes.tsx` (new)

**Modifications**:

- New component consuming `renderState` from the existing telemetry bus
  (`bus.ts` already carries `renderState` and both emitters publish it).
- Jet geometry (position and direction, body axes) must come from the sim-core
  public export of the thruster specs — do not re-declare jet positions in the
  web layer, or the two will drift.
- Render each plume as a cheap additive cone/sprite scaled by duty, oriented
  along `-direction_body` (exhaust opposes thrust). Mount inside the chaser's
  body-frame group so plumes inherit its transform.
- **Performance**: 16 plumes must not allocate per frame. Pre-build geometry and
  materials once; drive only scale/opacity per frame from a ref. Keep the whole
  effect inside the existing 60 fps budget on integrated GPUs.
- Plumes are additive and must respect the established HDR/bloom contract — only
  deliberate highlights should exceed luminance 1.0, or bloom will smear.

### 6. Procedural flight soundscape

**File**: `apps/web/src/hud/flightAudio.ts` (new), wired from the scene/HUD root

**Design**: follows `panelAudio.ts` — synthesized, lazy `AudioContext`, resumes
on first user gesture, fails silently before interaction.

- **RCS**: a *single pooled* filtered-noise voice whose gain tracks aggregate jet
  duty, plus a short attack transient on firing onset. Do **not** spawn a node
  per jet per tick — 16 jets at 10 Hz would create ~160 nodes/second.
- **Ambient**: low-frequency cabin hum, steady, well below the RCS bed.
- **Contact**: a thump on **physical contact only** — fire on a transition into
  `DOCKED` or `COLLISION`. Do **not** include `ABORT`: it is an abort-command
  latch, not a contact event, and would thump with nothing touching. Abort is
  covered by its own stinger.
- **Outcome stingers**: `PASSIVE_ABORT` and `WINDOW_MISSED` are **not** telemetry
  values — they are `ScenarioUiState` outcomes, and `WINDOW_MISSED` never
  reaches `TelemetryFrame` at all. Pick one and state it in the implementation:
  either (a) add a scenario-outcome channel to the telemetry bus, or (b) let
  `flightAudio` subscribe to the scenario store for MISSION-mode stingers while
  taking contact cues from telemetry. Option (b) is lighter and keeps sim-core
  untouched; option (a) is tidier if other consumers later want the same signal.
  Sandbox mode has no scenario outcomes, so stingers must degrade silently there.
- **Master volume/mute placement.** It must **not** go on `SwitchPanel`, which
  returns null unless MISSION (`SwitchPanel.tsx:100`) *and* is mounted inside a
  MISSION-only block in `Hud.tsx` — flight audio plays in SANDBOX too, so the
  control would be unreachable exactly where it is most needed. Put it on an
  always-mounted HUD surface (e.g. the mode bar or a small always-present audio
  affordance).
- **Shared master gain.** Route both `panelAudio` and `flightAudio` through one
  shared master `GainNode` so a single mute covers clicks, alarm, RCS, ambient,
  and stingers. This requires factoring the currently module-local
  `AudioContext` in `panelAudio.ts` into a small shared audio-context module that
  both files use — otherwise the two layers each own a context and the mute only
  covers half the sound.

**Constraint**: audio is a wall-clock, browser-side concern. It must read the
telemetry/render bus only, and must never feed back into sim state — sim-core
stays free of any audio coupling.

### 7. Authority switch UI + keybind

**File**: `apps/web/src/hud/SwitchPanel.tsx`, `apps/web/src/input/bindings.ts`, `apps/web/src/input/manualControls.ts`

**Modifications**:

- Add a `MANUAL_AUTH` two-position control to the switch panel emitting the
  `setManualAuthority` command, styled with the existing panel conventions and
  click sound.
- Add a keybind following the single-source bindings table so the keybinds
  overlay (`H`) picks it up automatically.
- Surface the active authority level in the HUD mode bar next to AUTO/MANUAL and
  RATE/PULSE.

## Technical Considerations

- **Pattern Usage**: authority is an operator command through the public
  `SimLoop` surface, matching `setController` / `setNavSource`; plumes and audio
  consume the telemetry/render bus only.
- **Package Boundary**: all rendering and audio live in `apps/web`; sim-core
  gains no DOM or audio dependency. Jet geometry is read from sim-core's public
  export rather than duplicated in the web layer.
- **Conventions**: jet positions/directions stay in body axes and SI; duty is
  dimensionless 0–1; any deg/s figures shown to the pilot convert at the UI
  boundary only.
- **Determinism**: authority changes flow through the command API on sim time,
  so `(scenario, seed, inputs)` still determines a run. Audio and plumes are
  wall-clock render-side and must never influence sim state.
- **Verification**: the manual rate loop needs a step-response invariant test
  (reaches and holds commanded rate within a bounded time, bounded overshoot) —
  the analogue of the existing oracle discipline for a control loop.
- **Performance**: 16 plumes with no per-frame allocation; one pooled audio voice
  rather than per-jet nodes; 60 fps budget on integrated GPUs preserved.
- **Edge Cases**: authority switched mid-maneuver (integrator/reference reset);
  stuck-open jet plume must render while FSW believes the jet is closed;
  propellant depletion scaling duty toward zero; audio before first user gesture;
  `HIGH` authority combined with translation demand must not re-trigger the
  v0.4.0 tumble.

## Type Definitions

- `ManualAuthority = 'LOW' | 'HIGH'`
- `MANUAL_AUTHORITY_PRESETS: Record<ManualAuthority, ManualLimitPreset>` where
  `ManualLimitPreset = { maxRate_rps; maxVelocity_mps; pulseForce_N; pulseTorque_Nm; manualForceLimit_N; kp?: Vec3; kd?: Vec3 }`.
  **The gain fields are optional on purpose**: `LOW` omits them, and omission is
  the sentinel meaning *inherit the resolved AUTO gains*. `HIGH` supplies both
  explicitly. This is what lets `LOW` track a caller's custom AUTO gains instead
  of freezing today's defaults into the table.
- `ResolvedManualLimits = { maxRate_rps; maxVelocity_mps; pulseForce_N; pulseTorque_Nm; manualForceLimit_N; kp_Nm_per_rad; kd_Nms_per_rad }`
  — the accessor result. Gains are **non-optional here**: resolution has already
  happened, so `LOW`'s inheritance is collapsed to concrete values. Returning
  gains is required for `getResolvedManualLimits()` to be the single resolution
  point it claims to be.
- `AttitudeControllerConfig` gains `manualKp_Nm_per_rad`, `manualKd_Nms_per_rad`,
  `manualForceLimit_N`, and `initialManualAuthority`
- `RenderState` gains per-jet normalized duty (`Record<string, number>`)
- `TelemetryFrame` gains the active authority level

## Performance & Cost Impact

Plumes add 16 lightweight additive meshes with per-frame scalar updates only.
Audio adds one steady noise voice plus a hum and occasional one-shots. Neither
touches the sim tick. The sim-core change is a `Record` copy per render-state
read; keep it shallow.

## Backward Compatibility

Additive. Omitting the new config yields today's behavior exactly, because
authority defaults to `LOW` and the `LOW` preset's shaping limits are today's
values while its manual gains resolve to the AUTO gains **as configured** (see
"inherits by reference" above). A caller with custom AUTO gains therefore sees no
change either. No scenario schema change — `schema_version` stays 1.
