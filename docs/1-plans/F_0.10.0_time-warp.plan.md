# Time-Rate Control (Time Warp) Implementation Plan

## Overview

KSP-style time-rate control across the whole sim: pause (0×), slow motion
(0.25×, 0.5×), real time, physics warp (2×, 4×, 10× — everything still
simulated), and rails warp (50×, 100×, 1000× — analytic coast on the CW closed
form with flight software suspended). Keybound with a HUD indicator, available
in SANDBOX **and** MISSION (the scenario-mode warp ban is lifted by owner
decision; the director auto-drops warp when a beat fires so scripted moments
are never skipped). Ships as v0.10.0 after the space-to-ground release.

## Problem Statement

Wall clock is currently welded to sim time at 1×: the emitters pace one
sim-second per wall-second and no public command can change it. Docking
contact analysis wants slow motion; long coasts (and every future
orbital-mechanics feature — Earth-Moon-Sun transfers take days) want warp.
The architecture already keeps sim-time pure (fixed-step, no wall-clock
coupling in sim-core), which is exactly what makes rate control safe to add —
pacing is a render-side concern, and rails is an analytic sim-core stride.

## Solution Architecture

Three layers, honouring the existing seams:

1. **sim-core: rate as a deterministic command + rails as analytic strides.**
   - `SET_TIME_RATE` joins the public command API (the `setManualAuthority`
     pattern): a discrete rate ladder, validated, recorded in telemetry. The
     rate itself does NOT alter physics math — at physics rates it only tells
     the *host* how many fixed steps to run per wall frame.
   - **Rails coast** (`railsCoast.ts`, new) — defined as a *per-tick analytic
     fast path*, not variable-length strides: rails advances in exact 0.1 s
     FSW-tick increments. Each rails tick replaces truth RK4 with the CW
     state-transition matrix (already in the MPC machinery) and closed-form
     torque-free attitude propagation, forces thrusters idle, skips
     sensors/measurements/controller, and runs the nav filter's normal
     PREDICT step (means AND covariance through the same 10 Hz recurrence the
     live filter uses — no measurement update). **MEKF rate source during
     rails**: with gyros skipped, the MEKF propagates its attitude mean with
     its last bias-corrected rate estimate held constant — a documented coast
     assumption whose error is bounded by the eligibility guard's low-rate
     requirement and honestly reflected in the Q-grown covariance; the first
     live measurements after exit correct the residual. Consequences, each by
     construction rather than by extra mechanism: (a) filter means,
     covariance, and timestamps stay current, so rails-exit is just "resume
     measurements" with honestly grown uncertainty; (b) the covariance oracle
     is exact — a rails span is bit-comparable to the same span of
     predict-only filter ticks; (c) wall-frame slicing cannot affect results —
     wall frames only choose how many deterministic 0.1 s rails ticks run.
     Cost: O(simulated_seconds / 0.1) small fixed-size matrix ops,
     governor-bounded per wall frame and measured at 1000× in Phase 4.
     FSW controller/guidance state: command history cleared and the MPC plan
     invalidated at rails entry; MPC re-solves at its first live tick after
     exit.
   - **Eligibility guard**: rails requires *actual jet state* idle (commanded
     AND stuck-open — a stuck-open jet is continuous thrust, rails
     ineligible), body rates below a threshold, range above a proximity gate,
     and closing rate below a bound. During rails, each tick re-checks the
     analytic trajectory against the proximity/keep-out boundary AND the
     approach-corridor cone (the same acceptance monitors that are suspended
     on rails) and auto-drops to 1× at the first predicted crossing of any of
     them — no monitored boundary can be crossed while its monitor sleeps.
   - **Event-horizon chunking**: rails ticks never cross a scheduled sim-time
     event — the loop advances to `min(target, next scheduled event)` in tick
     multiples, so director beats, clock expiry, and any future scheduled
     event fire at their exact sim-time. Rails work is governor-bounded per
     wall frame like physics stepping — never O(1), never unbounded.
   - **Determinism contract (stated precisely)**: a run is fully determined by
     (scenario, seed, command sequence with sim-time stamps) — warp commands
     are part of the input record. A warped run is NOT bit-identical to an
     unwarped run of "the same" flight: rails ticks consume no sensor-noise
     draws, so the RNG stream position differs by construction. The
     determinism oracle is warp-inclusive replay, not cross-rate identity.
   - **Authoritative rate state**: `setTimeRate` returns — and a synchronous
     `getTimeRateState()` exposes — `{ commanded, effective, mode, rejection?,
     cause: 'COMMAND' | 'CLAMP' | 'DIRECTOR_DROP' | 'SAFETY_DROP' }`. Hosts
     (emitter pacing, HUD force-drop flash) read this state directly; they
     never infer rate from telemetry, which pauses during rails. The emitters
     publish a lightweight host-status snapshot (effective rate, mode, sim
     clock) to the HUD store every wall frame from `getTimeRateState()` +
     the sim clock — so the rate indicator and clock stay live during rails
     even though `TelemetryFrame`s (an FSW product) do not flow. The replay
     record's warp authority is a timestamped append-only COMMAND LOG (every
     `setTimeRate` with sim-time, source, and resulting effective rate/mode,
     including CORE_SAFETY drops) — telemetry frames cannot carry rails
     history because none flow during rails; the `time_rate`/`time_mode`
     fields simply stamp the frames that do flow.

2. **scenario: director-controlled auto-drop + spec revision.**
   - The director may command rates through the same public command API the UI
     uses (honesty invariant untouched). When a beat fires or an alarm raises,
     the director commands 1× — warp never skips a teaching moment.
   - **MISSION stepping path**: the director's existing beat/expiry boundary
     loop switches from `stepTo` to the same rails-aware absolute-time entry
     the sandbox emitter uses (`advanceTo(simTime)`), with beat times and T-0
     registered as scheduled events — one stepping API, both hosts, no
     rails-bypasses-director hole.
   - **Telemetry-gated holds vs rails**: the director declares hold-gated
     windows to the core through a public interlock command,
     `setRailsInterlock(active, 'ACTIVE_BEAT')` (source DIRECTOR, same command
     surface as everything else) — while the interlock is set, rails is
     REJECTED (clamped to the physics ceiling, `rejection: 'ACTIVE_BEAT'`);
     the director RECOMPUTES it after every beat transition as
     `beats.some(active && telemetryHold)` — set-when-any, clear-when-none —
     so overlapping hold beats can never unlock rails while one remains
     active. A hold can neither run nor falsely clear from
     stale frames while telemetry is paused; physics rates keep telemetry
     flowing, so holds behave normally there.
   - `docs/scenario-mode-spec.md` §1.4 is revised: "Pause pauses the scenario
     clock. Time-warp is permitted; the director drops the rate to 1× when a
     beat fires or an alarm raises." §7 gains a warp acceptance test (below).
     The paste-ready prompt in §8 drops the "time-warp disabled" constraint.

3. **apps/web: pacing multiplier + governor + controls.**
   - Both emitters (`simEmitter`, `scenarioEmitter`) multiply wall delta by
     the effective rate (from `getTimeRateState`) to decide how much sim-time
     to advance per frame, capped by a max-steps-per-frame governor so a slow
     machine degrades to slower wall progress — never dropped sim steps, never
     altered physics. **Backlog policy**: wall-time debt beyond one frame's
     budget is DISCARDED (the sim simply progresses slower than the nominal
     rate); debt never accumulates, so input latency stays bounded on an
     overloaded machine. The governor is render-side pacing only; sim output
     is a pure function of sim-time regardless of how wall time slices it.
   - Keybinds: `,` rate down / `.` rate up (KSP muscle memory), `P` pause
     toggle (bindings-layer conflict check at implementation; the keybinds
     overlay documents them). HUD: rate readout in the mode bar (`1×`, `10×`,
     `RAILS 100×`, `PAUSED`), amber when above 1×, plus a brief flash when the
     director force-drops the rate in MISSION.
   - MISSION: fully enabled per owner decision; ANALYSIS (Monte Carlo) is
     unaffected — batch runs already execute as fast as the worker can step.

## Implementation Details

### 1. sim-core — command + rails

**Files**: `packages/sim-core/src/sim.ts`, `types.ts`,
`railsCoast.ts` (new), `cw.ts` (reuse STM export), `index.ts` (public surface).

- `types.ts`: `TIME_RATE_LADDER` (0, 0.25, 0.5, 1, 2, 4, 10, 50, 100, 1000)
  with the physics ceiling marked; `TelemetryFrame` gains `time_rate` and
  `time_mode: 'PHYSICS' | 'RAILS' | 'PAUSED'`; rails-eligibility thresholds as
  named constants.
- `sim.ts`: `setTimeRate(rate)` command (validated against the ladder,
  clamped when rails is ineligible, latched, returns the rate-state);
  synchronous `getTimeRateState()`; `advanceTo(simTime)` host entry — the ONE
  stepping API both the sandbox emitters and the MISSION director use — that
  runs fixed physics steps or 0.1 s rails ticks up to `min(target, next
  scheduled event)`, with `scheduleEvent(t)` registration. **Early-return
  contract**: any rate-changing event inside `advanceTo` (scheduled event
  reached, SAFETY_DROP) stops stepping IMMEDIATELY and returns
  `{ reachedTime, stopReason }`; the caller discards its remaining wall-time
  budget for that frame and re-plans from the new authoritative rate — a drop
  can never continue simulating toward a stale target. Director drops are a
  HOST-side consequence of `SCHEDULED_EVENT` (the director issues the 1×
  command after control returns), never a core stop reason.
- `setTimeRate(rate, source)` takes an explicit source
  (`'OPERATOR' | 'DIRECTOR' | 'CORE_SAFETY'`) — the core cannot infer its
  caller, so cause attribution is an input, not an inference.
- `railsCoast.ts`: per-0.1 s analytic tick — CW STM translation, torque-free
  attitude propagation (closed-form for the axisymmetric/principal case;
  fixed small substeps of the free Euler equations otherwise, documented as
  rails-internal), filter predict delegation, safety-boundary crossing check,
  eligibility predicate (incl. stuck-open jet detection from truth jet state).
- `fsw.ts` / `ekf.ts` / `mekf.ts` / `mpc.ts`: rails entry/exit hooks —
  predict-only filter ticks during rails (means + covariance + timestamps),
  command-history clear and MPC plan invalidation at entry, measurement
  resume at exit.

### 2. scenario — director drop + spec

**Files**: `packages/scenario/src/director.ts`, `acceptance.test.ts`,
`docs/scenario-mode-spec.md`.

- Director: on beat fire or alarm raise, issue `SET_TIME_RATE 1` through
  `ScenarioSimPort` (type gains the command — still `Omit` of truth/render
  getters); register beat times + T-0 as scheduled events for chunking.
- Spec §1.4 revision + §7.6 acceptance test: a warped perfect-operator run
  that commands a ≥50× RAILS interval during a quiet coast segment (plus 10×
  physics elsewhere) still ends `DOCKED`; beats fire at their exact
  `t_start_s`; rails exits with filter re-convergence; and replaying the
  identical warp-inclusive command record reproduces the trajectory hash.

### 3. apps/web — pacing, keys, HUD

**Files**: `apps/web/src/telemetry/simEmitter.ts`, `scenarioEmitter.ts`,
`apps/web/src/input/bindings.ts`, `manualControls.ts`,
`apps/web/src/hud/ModeBar.tsx`, `KeybindsOverlay.tsx`.

- Emitters: rate-scaled sim advance + max-steps governor (config constants).
- Input: `,` / `.` / `P` with the FLY/manual precedence rules from v0.9.0
  respected; keys emit the public command, never touch state directly.
- HUD: mode-bar rate indicator + MISSION force-drop flash; keybinds overlay
  rows.

## Technical Considerations

- **Pattern Usage**: `setManualAuthority` deterministic-command pattern; CW
  STM reuse from the MPC machinery; config-derived constants; KSP interaction
  grammar (`,`/`.`, auto-drop like KSP's warp-stop alarms).
- **Package Boundary**: rails math is pure sim-core; the director uses only
  the public command API (compile-enforced via `ScenarioSimPort`); web touches
  emitters/HUD/input only.
- **Conventions**: sim-time seconds everywhere; the fixed-step rates
  (100/10/1 Hz) are unchanged at all physics rates — warp changes how many
  steps per wall frame, never the step size. ARCHI's Time convention gains
  one sentence (rate ladder + rails stride) at release.
- **Determinism**: warp commands are sim-time-stamped inputs; replay oracle
  includes them. Rails strides are closed-form (no RNG); physics rates leave
  the per-tick RNG draw sequence untouched.
- **Verification**: rails-vs-numeric oracle (per-tick CW STM path vs RK4 at
  1× over the same sim-span, position/velocity within integration tolerance);
  torque-free attitude ticks vs RK4 momentum conservation; rails covariance
  span bit-equal to the same span of predict-only live-filter ticks (exact by
  construction — the oracle proves the wiring); safety-crossing auto-drop
  property test (a rails run toward the gate exits before crossing);
  eligibility guard properties incl. stuck-open jets; event-horizon chunking
  lands beats on exact ticks; wall-slicing invariance (two different
  frame-slicing patterns of the same advanceTo sequence produce identical
  hashes); director force-drop boundary unit test (advanceTo returns
  `SCHEDULED_EVENT` at the beat tick, the director then issues the 1×
  DIRECTOR command, remaining budget discarded); command-log replay
  reproduces rails entry/exit exactly.
- **Performance**: 10× physics = 1000 truth steps + 100 FSW ticks + 10 QP
  solves per wall-second — the governor caps per-frame work so render never
  stalls; rails cost is governor-bounded per wall frame (see Performance).
- **Edge Cases**: rate change mid-frame (applies at next sim tick); rails
  request while ineligible (clamps to 10× with HUD notice); MPC horizon
  invalidated by a rails stride (force re-solve on exit — it re-solves at its
  next 1 Hz tick anyway); pause during MISSION (scenario clock pauses, spec
  rule unchanged); docking contact impossible on rails by the proximity gate.

## Type Definitions

- `TimeRate = 0 | 0.25 | 0.5 | 1 | 2 | 4 | 10 | 50 | 100 | 1000`
- `AdvanceResult { reachedTime: number; stopReason: 'TARGET_REACHED' | 'SCHEDULED_EVENT' | 'SAFETY_DROP' | 'PAUSED' }` — the core never emits a director drop: it stops at `SCHEDULED_EVENT`, control returns, and the director (an external actor) converts that into `setTimeRate(1, 'DIRECTOR')`, which the log records
- `TimeRateChangeRecord { simTime: number; commanded: TimeRate; effective: TimeRate; mode: TimeMode; source: 'OPERATOR' | 'DIRECTOR' | 'CORE_SAFETY' }` (append-only command log, the warp replay authority; exposed via a public
  `getTimeRateLog()` snapshot. **Replay semantics**: replay injects ONLY
  `OPERATOR` records as inputs — `DIRECTOR` and `CORE_SAFETY` records are
  recomputed by the deterministic director/physics during the replay and
  VERIFIED equal to the recorded log, which is itself the determinism oracle)
- `TimeMode = 'PHYSICS' | 'RAILS' | 'PAUSED'`
- `TelemetryFrame` += `{ time_rate: TimeRate; time_mode: TimeMode }`
- `RailsEligibility { eligible: boolean; reason?: 'THRUSTING' | 'RATES' | 'PROXIMITY' | 'CLOSING' | 'ACTIVE_BEAT' }`

## Performance & Cost Impact

Physics warp ≤10× is CPU-bounded by the QP at 10 solves/wall-second — measured
against the frame governor, not guessed. Rails cost is O(simulated_seconds /
0.1) small fixed-size matrix ops — ~10,000 rails ticks per wall-second at
1000×, bounded by the same per-frame governor; Phase 4 records a measured
frame-time checkpoint at 1000×. No GPU
impact; no asset impact.

## Backward Compatibility

unaffected except telemetry-shape assertions (two added fields). The scenario
spec revision is versioned in place (spec text, not schema — `schema_version`
stays 1; no scenario data changes).
