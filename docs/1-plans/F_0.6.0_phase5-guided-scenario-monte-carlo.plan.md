# Guided Scenario Mode + Monte Carlo Implementation Plan

## Overview

Adds Phase 5 to the roadmap: a scripted "Mission Mode" (`FINAL_APPROACH_01`) that
turns the sandbox into a timed emergency drill per `docs/scenario-mode-spec.md`,
and an in-app Monte Carlo analysis mode that batch-runs that scenario across many
seeds to report success rate, prop margin, and abort-safety statistics with
histogram visualization. Both are new capabilities layered on top of the existing
sim-core/apps-web split; neither changes truth physics.

Video capture/recording is explicitly **out of scope** — a manual, post-ship task.

## Problem Statement

Today `apps/web` has exactly one always-on mode: a continuous sandbox sim driven
by `simEmitter.ts` (`setInterval`, wall-clock paced, fixed seed). There is no
scenario concept, no scripted-failure timeline, no switch panel, and no batch/
headless run capability — `ekf.test.ts`/`mekf.test.ts` prove the sim can run
seeded Monte Carlo batches, but only inside Vitest, not as a user-facing feature.
Three `PlayerAction`/`FailureInjection` kinds required by the spec's own schema
(`SET_NAV_SOURCE`, `GUIDANCE_FAULT`, `VEL_BIAS`) have no corresponding public
`SimLoop` method today, so the spec cannot be implemented against the current
public API alone.

## Solution Architecture

- **New pure-TS workspace package `packages/scenario`** (peer to `sim-core`,
  same "no React/Three/DOM" rule) owns the schema types, `FINAL_APPROACH_01`
  data, `ScenarioDirector`, the perfect-operator bot, and the Monte Carlo batch
  runner. It imports `@docking/sim-core` **only through its public export map**
  (`sim-core/src/index.ts`), never deep-imports `sim-core/src/*` — this is what
  makes the honesty-invariant static check (spec §7.4) enforceable, and lets the
  Monte Carlo harness run headless in Vitest exactly like the existing filter
  ANEES tests.
- **Sim-core gains three additive public `SimLoop` methods** to close the gap
  above: `setNavSource`, `injectGuidanceFault`/`clearGuidanceFault`,
  `injectVelocityBias`. These are new *command-surface* entry points operating
  within existing physics (attitude-measurement selection, command-freeze,
  truth-velocity nudge) — not new dynamics or sensor models — so they stay
  inside the spec's own "no new physics" boundary while realizing failure kinds
  the spec's schema (§3, explicitly in-scope) already defines.
- **`SimOutcome` is not renamed.** `sim-core`'s existing `'ABORT'` literal stays;
  `ScenarioDirector` maps it 1:1 to the spec's `'PASSIVE_ABORT'` `OutcomeId` at
  the director boundary, and owns `'WINDOW_MISSED'` entirely at that layer (T-0
  clock expiry is a scenario-timing concept sim-core has no reason to know
  about). This keeps the change additive/non-breaking for existing sim-core
  tests and HUD literals. Flagged explicitly for reviewer scrutiny — the
  alternative (renaming `SimOutcome` for terminology consistency) was rejected
  to minimize blast radius across `sim.test.ts`, `OutcomeBanner.tsx`, and
  `CautionWarningPanel.tsx`.
- **`apps/web` gains a top-level app-mode switch**: `SANDBOX` (today's always-on
  behavior, unchanged, stays default), `MISSION` (drives a
  `ScenarioDirector`-wrapped `SimLoop` for `FINAL_APPROACH_01`, sim-time only,
  no time-warp per spec rule 4), `ANALYSIS` (Monte Carlo screen). This lives in
  a new store, not `viewStore.ts` (which is camera-only and must stay that way).
- **Monte Carlo runs off the main thread** via a Web Worker pool — `sim-core`
  already "runs identically in page, workers, and Node" per `ARCHI.md`, so each
  worker runs a shard of seeded `FINAL_APPROACH_01` runs (director + perfect-
  operator bot, no wall-clock pacing) and posts back per-run outcome/stats for
  progressive aggregation in a results panel using `uPlot` (currently
  uninstalled — `ARCHI.md`'s "uPlot planned" note is accurate).

## Implementation Details

### Phase 1: sim-core gap-filling

#### 1. `packages/sim-core/src/mekf.ts`

**File**: `packages/sim-core/src/mekf.ts`

**Current state**: MEKF attitude filter always applies the star-tracker
attitude measurement update every tick; no concept of measurement-source
selection.

**Modifications**:

- Add a `navSource: 'PRIMARY' | 'BACKUP'` input to the MEKF tick/config. When
  `'BACKUP'`, skip the star-tracker attitude measurement update and propagate
  attitude from gyro integration only (dead-reckoning), so a biased/degraded
  star tracker (Beat B1) is fully rejected once the operator switches source —
  matches spec's `clears_when` check on `NEES` dropping.

#### 2. `packages/sim-core/src/fsw.ts`

**File**: `packages/sim-core/src/fsw.ts`

**Modifications**:

- Thread the new `navSource` selection from `FswTick`'s command surface into
  the MEKF call (near the existing `setController`/`setControlMode` command
  handlers, ~line 436).
- Add a `guidanceFrozen` internal flag: when set, guidance/controller output
  holds at the last commanded target instead of updating (`GUIDANCE_FAULT` /
  `FREEZE_CMDS`), until `setControlMode('MANUAL')` is called — matches Beat
  B4's `required_action`.
- Add a `corridor_level: 'NOMINAL' | 'CAUTION' | 'VIOLATION'` output field,
  sourced from the existing two-level corridor monitor result that already
  drives the passive-abort trigger — single source of truth, no duplicated
  threshold logic in `packages/scenario`.

#### 3. `packages/sim-core/src/sim.ts`

**File**: `packages/sim-core/src/sim.ts`

**Current state**: `SimLoop` interface (lines 55-68) covers
`isolateThruster`, `injectThrusterStuck`, `setController`, `commandAbort`,
`setControlMode`, `setSensorDegrade`/`clearSensorDegrade`.

**Modifications**:

- Add three methods to `SimLoop`: `setNavSource(source: NavSource)`,
  `injectGuidanceFault()` / `clearGuidanceFault()`, `injectVelocityBias(dv_mps:
  Vec3)`. Wire each into `createSimLoop` (line 167) alongside the existing
  command dispatch.
- `injectVelocityBias` is implemented **entirely in `sim.ts`**, not `fsw.ts`:
  it stores a pending `dv_mps` on the truth-side loop state and applies it as
  a one-shot nudge to truth velocity at the start of the next truth-integrator
  tick, then clears the pending value. `fsw.ts` never touches truth state
  (`ARCHI.md`'s package-boundary rule) — this method must not be routed
  through `FswTick`.

#### 4. `packages/sim-core/src/sensors.ts`

**File**: `packages/sim-core/src/sensors.ts`

**Modifications**:

- `SensorDegradeConfig.noiseMultiplier` (line 27) currently applies uniformly
  to all channels. Add a `channel: 'RANGE' | 'ATTITUDE' | 'ALL'` selector so
  Beat B1's escalation (`RANGE`, `NOISE_X10`) can scale range noise only,
  matching the spec's per-sensor `NAV_DEGRADE` targeting.
- `SensorBiasRamp.attitude_rad` (line 9) is a `Vec3`, not a scalar — the
  existing fixed-target ramp already biases all three attitude axes
  independently. Beat B1's trigger supplies only a scalar `deg_per_min` (an
  open-ended rate, not a target/duration pair), and the ramp must keep
  growing until the operator clears it by switching nav source, not stop on
  its own. Add a continuous-rate mode — `attitudeBiasRatePerMin_rad?: Vec3`
  — that grows `attitude_rad` bias linearly forever (until
  `clearSensorDegrade()` is called), alongside the existing fixed-target/
  duration mode. The `packages/scenario` adapter converts the spec's scalar
  `deg_per_min` into this `Vec3` by applying the rate equally to all three
  axes (`[r, r, r]` in rad/min after deg→rad conversion) — the spec doesn't
  constrain which axis the star-tracker bias grows along, so an even
  3-axis split is the simplest defensible default; flagged for scrutiny if a
  more specific axis convention is wanted later.

#### 5. `packages/sim-core/src/types.ts`

**File**: `packages/sim-core/src/types.ts`

**Modifications**:

#### 9b. `packages/scenario/src/scenarioToSimConfig.ts`

**File**: `packages/scenario/src/scenarioToSimConfig.ts` (new)

`scenarioToSimConfig(scenario.initial): SimConfig` — the missing conversion
from spec's `InitialConditions` to `sim-core`'s `SimConfig`/
`SimInitialConditions`, defined explicitly (not left implicit):

- `rel_position_m`/`rel_velocity_mps` map straight through (already Hill-
  frame, already SI) to `SimInitialConditions`' position/velocity.
- `attitude_error_deg` composes as a small-angle rotation offset *from* the
  nominal docking-port-forward LVLH-hold attitude (the same nominal used by
  the sandbox default), converted to the initial truth quaternion; degrees →
  radians at this boundary per `ARCHI.md`'s convention.
  `body_rates_dps` → `rad/s` the same way.
- EKF/MEKF priors seed with zero bias and the same initial covariance used by
  the sandbox default config (no scenario-specific filter tuning).
- `prop_kg` maps to **two** places, since truth and FSW track propellant
  separately: `SimInitialConditions.prop_kg` (`sim.ts:35`, the truth-side
  tank) and `FswConfig.massModel.initialProp_kg` (`fsw.ts:40`, FSW's own
  propellant estimate). Both must be set from the same `InitialConditions.
  prop_kg` value or the truth/estimate mass models start inconsistent.
- Immediately after `createSimLoop`, the director issues
  `setController(initial.controller)`, `setControlMode(initial.control_mode)`,
  `setNavSource(initial.nav_source)` to realize the remaining `InitialConditions`
  fields that aren't part of `SimConfig` itself.

Used by both `scenarioEmitter.ts` (live Mission Mode) and `monteCarlo.ts`
(batch runs) so the two never diverge in how a scenario is instantiated.

#### 10. `packages/scenario/src/director.ts`

**File**: `packages/scenario/src/director.ts` (new)

`createScenarioDirector(scenario, simPort)` implementing the per-tick order
from spec §5 (advance clock → fire due beats → evaluate `clears_when` →
apply escalation on window expiry → evaluate monitors/resolve outcome → emit UI
state). `simPort` is typed as `ScenarioSimPort` — a narrowed interface
(`Omit<SimLoop, 'getTruthState' | 'getRenderState'>`, `SimLoop` imported from
`@docking/sim-core`'s public API) **defined in `packages/scenario`** (not
`sim-core` — the narrowing is a scenario-domain concern; `sim-core` stays
free of any scenario-specific type). Typing the director against this
narrowed port makes calling truth/render getters a **compile-time error**,
enforcing the honesty invariant structurally in addition to the ESLint
import-boundary rule (spec §7.4).

`director.ts` also owns the `BRIEFING → RUNNING → DEBRIEF` phase.
`tick()` is a **full no-op while `phase === 'BRIEFING'`** — it does not call
`simPort.stepTo()` at all, so truth physics does not silently advance while
the briefing card is on screen (not just the scenario clock label). A
`launch()` method transitions `BRIEFING → RUNNING` and is the only thing
that lets `tick()` start calling `stepTo`. Retry resets straight to
`RUNNING` with a fresh `simPort` instance (briefing already read). The
Monte Carlo path (item 14) has no human to click Launch, so its single-run
driver calls `launch()` immediately after construction, before its tight
loop — never leaves a run stuck in `BRIEFING`.

#### 11. `packages/scenario/src/perfectOperatorBot.ts`

**File**: `packages/scenario/src/perfectOperatorBot.ts` (new)

Scripted policy that reacts to each beat's `prompts.hint_control`/
`required_action` within `response_window_s` and drives canned manual-fly
inputs for Beat B4. Used by both the completability acceptance test (§7.3) and
the Monte Carlo harness (every MC run needs an actor, since a human isn't
present).

#### 12. `packages/scenario/src/monteCarlo.ts`

**File**: `packages/scenario/src/monteCarlo.ts` (new)

Two exports:

- `runMonteCarloRun(scenario, globalIndex: number, masterSeed):
  MonteCarloRunResult` — the primitive. Derives its seed via
  `deriveSeed(masterSeed, `run-${globalIndex}`)` (deterministic and
  collision-free across shards by construction, since `globalIndex` values
  are globally unique — chosen over the flat-offset pattern in
  `ekf.test.ts`, which is fine for a fixed single-process test but not for
  independent workers). Builds the sim via `scenarioToSimConfig`, wraps it
  in `ScenarioDirector`, calls `launch()` immediately (no briefing wait —
  see item 12), then drives `perfectOperatorBot` + `tick()` to completion
  (no wall-clock pacing — tight loop until an outcome latches or
  `clock.duration_s` elapses).
- `runMonteCarloBatch(scenario, runIndices: number[], masterSeed):
  MonteCarloRunResult[]` — a thin `runIndices.map(i =>
  runMonteCarloRun(scenario, i, masterSeed))` convenience wrapper, used by
  the non-worker fallback path and by acceptance/determinism tests. **Not**
  used by `monteCarloWorker.ts` (item 33) — a worker calls
  `runMonteCarloRun` once per index in its own loop and posts a message
  after each call, which is what makes per-run progress genuinely
  progressive rather than only available after the whole shard finishes.

Per-run result (`MonteCarloRunResult`): `{ seed, outcome: OutcomeId,
prop_consumed_kg, time_margin_s, corridor_violation_count, score, grade }`,
computed as:

- `prop_consumed_kg = scenario.initial.prop_kg - finalFrame.prop_kg` (both
  already exist on `SimInitialConditions`/`TelemetryFrame` — no new sim-core
  field needed here).
- `time_margin_s = clock.duration_s - t_outcome_s` if `outcome === 'DOCKED'`,
  else `0` (only a completed capture earns time margin).
- `corridor_violation_count` = number of `corridor_level` transitions into
  `'CAUTION'` during the run (soft excursions; a `'VIOLATION'`-level entry
  ends the run via `PASSIVE_ABORT` and is scored through `outcome`, not
  double-counted here).
- For `outcome === 'DOCKED'`: `score = 100 + scoring.weights.prop_kg *
  prop_consumed_kg + scoring.weights.time_margin_s * time_margin_s +
  scoring.weights.corridor_violations * corridor_violation_count`, `grade` =
  highest of `A`/`B`/`C` whose `grade_bounds` threshold `score` meets or
  exceeds, else ungraded (`'F'`). A base of 100 is necessary, not just
  cosmetic: with `FINAL_APPROACH_01`'s verbatim weights/bounds
  (`prop_kg: -3.0`, `time_margin_s: 0.2`, `corridor_violations: -15`,
  `A: 85`), a bare weights-only sum tops out around 72 for an idealized
  zero-cost run — below even the `B` bound — making the spec's own grade
  bounds structurally unreachable. Starting from a full-credit baseline for
  completing the mission, then subtracting penalties/adding the small time
  bonus, is the only reading that makes the given bounds achievable.
- For any other `outcome` (`PASSIVE_ABORT`/`COLLISION`/`WINDOW_MISSED`):
  `score = 0`, `grade = 'F'` — the mission wasn't completed, so no
  propellant-efficiency credit applies.

## Technical Considerations

- **Pattern Usage**: `packages/scenario` follows `packages/sim-core`'s exact
  package shape (pure TS, Vitest, public `index.ts` export map). New HUD
  components follow `ModeBar.tsx`'s static-list-plus-telemetry-driven-`active`-
  class pattern. No parallel state-management mechanism introduced — all new
  UI state goes through Zustand stores consistent with `viewStore.ts`/`bus.ts`.
- **Package Boundary**: `packages/scenario` is pure TS, no DOM — the
  `ScenarioDirector` and Monte Carlo harness must run identically in Node
  (Vitest), a Web Worker, or the page, per `ARCHI.md`'s package-boundary rule.
  `apps/web` consumes `@docking/scenario` only through its public export map,
  same discipline as `@docking/sim-core`.
- **Honesty Invariant / Kernel Boundary**: enforced two ways. (1) spec §7.4's
  static check (director package imports only `@docking/sim-core`'s public
  API, never `sim-core/src/*` directly) is the sim-domain equivalent of
  ARCHI's kernel/UI boundary rule — implement as an ESLint
  `no-restricted-imports` rule scoped to `packages/scenario/**`, wired into
  the same CI job as `pnpm -r test`. (2) that alone doesn't stop the director
  calling `getTruthState()`/`getRenderState()`, since both are part of the
  public `SimLoop` interface — `director.ts` is typed against a narrowed
  `ScenarioSimPort` (`Omit<SimLoop, 'getTruthState' | 'getRenderState'>`,
  defined in `packages/scenario` itself, item 12) so calling either is a
  compile-time error, not just a lint convention.
- **Determinism**: `ScenarioDirector` and Monte Carlo both derive all
  randomness from `scenario.seed` (or `deriveSeed(masterSeed, ...)` for MC
  sub-runs) — no `Math.random`, no wall-clock reads anywhere in
  `packages/scenario`. Time-warp is disabled in `MISSION` mode, and pause
  freezes physics and the scenario clock **together** (they advance in the
  same `tick()` — pausing one but not the other would let a player stabilize
  the vehicle for free with the countdown frozen; spec rule 4) —
  `scenarioEmitter.ts` must reject/ignore any time-warp command while
  `appModeStore.mode === 'MISSION'`.
- **Outcome-type split**: `TelemetryFrame.outcome` (`sim-core`, truth-level:
  `'NONE'|'DOCKED'|'COLLISION'|'ABORT'`) and the director's `OutcomeId`
  (`scenario`, scenario-level: adds `'PASSIVE_ABORT'`/`'WINDOW_MISSED'`,
  1:1-maps `'ABORT'→'PASSIVE_ABORT'`) are two distinct, unmerged types by
  design — see Solution Architecture rationale. UI components must be
  explicit about which one they're reading.
- **Performance**: MPC's 1 Hz QP solve is the heaviest per-tick cost; a
  360-second scenario is 360 MPC solves per run. A few hundred Monte Carlo
  runs must not block the main thread or the render loop — mandatory Web
  Worker pool (sized to `navigator.hardwareConcurrency`), progressive
  aggregation with a cancel control, and a conservative default `runCount`
  (suggest 100, user-adjustable) rather than defaulting to thousands.
- **Edge Cases**: a beat's `guarantee` firing when `clears_when` is already
  satisfied at `t_start_s` (Beat B3, "player flew too well") must be exercised
  by a director test, not just documented; T-0 clock expiry racing a
  same-tick capture latch (spec §5 step 1, "unless capture already latched")
  needs an explicit ordering test; Monte Carlo cancellation mid-batch must
  leave the worker pool and `monteCarloStore` in a clean `IDLE` state, not a
  stuck `RUNNING` state.

## Performance & Cost Impact

- Sim-core additions (Phase 1) are O(1) per-tick branches — negligible cost
  added to the existing 100 Hz truth / 10 Hz FSW / 1 Hz MPC loop.
- `MISSION` mode's `scenarioEmitter.ts` adds one more per-tick evaluation
  (beat/monitor checks) on top of the existing FSW tick — negligible relative
  to the MPC QP solve.
- Monte Carlo is the real cost driver: N runs × up to 360 MPC solves each.
  Mandatory Web Worker pool keeps the main thread and render loop unaffected;
  default `runCount` kept conservative (see Edge Cases/Performance above) to
  keep a full batch in the tens-of-seconds range on typical hardware.

## Backward Compatibility

Fully additive. `SANDBOX` remains the default `appModeStore` mode and its code
path (`App.tsx`, `simEmitter.ts`, existing HUD components in their current
usage) is untouched. `SimOutcome` is not renamed (see Solution Architecture).
`TelemetryFrame` gains new fields only — no existing field removed or
retyped. `packages/scenario` is a new workspace package with no existing
consumers to break.

## Test Impact

- New oracle/acceptance tests in `packages/scenario`: the 5 tests from spec
  §7 (determinism, interactivity-is-load-bearing, completable-via-bot,
  honesty-invariant static import check, schema validation) — these become
  the new entries under `ARCHI.md`'s "Testing gate" for Phase 5.
- `packages/sim-core`: `mekf.test.ts` needs a nav-source `BACKUP` case (star
  tracker biased, backup selected, NEES recovers); `fsw.test.ts` needs a
  guidance-freeze case; `sim.test.ts` needs coverage of all three new
  `SimLoop` methods including `injectVelocityBias` (truth-layer only — not
  `fsw.test.ts`, per the package-boundary fix above), consistent with its
  existing determinism-test idiom (two seeded instances, `toEqual` frame
  comparison).
- Monte Carlo needs its own determinism test (same master seed ⇒ identical
  aggregate stats), a "zero-input-equivalent" sanity check reusing spec
  acceptance test §7.2's logic across the batch (no run should ever reach
  `DOCKED` with a bot that ignores every beat — bounds the bot fixture itself,
  not just one run), a scoring-formula unit test against hand-computed
  expected values for a fixed synthetic run result, and a seed-uniqueness
  regression across simulated shards (two disjoint `runIndices` arrays from
  the same `masterSeed` must never produce a shared seed).
- `apps/web`: `manualControls.ts`'s mode-aware routing needs a test/manual
  check that `MISSION` mode input reaches `scenarioEmitter`, not `simEmitter`;
  `BriefingCard`'s launch gate needs a check that the scenario clock does not
  advance before `launch()` is called.
- No existing `sim-core` test should need behavior changes — all Phase 1
  additions are new branches gated by new optional inputs, not changes to
  existing default behavior.
- No golden-file/export fixtures are affected — this feature does not touch
  Gerber/DXF/CST/PDF/SVG-equivalent export paths (not applicable to this
  project's exporters, which don't exist; noting for template completeness).
